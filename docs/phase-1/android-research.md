# Android technical research

Research checked official platform APIs and upstream implementation paths in November 2026. API availability indicates where to investigate. Release image, OEM policy, provisioning and distribution determine what actually works.

## Work profiles and public Android APIs

| Primitive | Behavior and engineering implication |
| --- | --- |
| Profile provisioning | `ACTION_PROVISION_MANAGED_PROFILE` and `isProvisioningAllowed` are available from API 21/24 respectively. On Android 12+ handle provisioning mode and admin-policy compliance where the OS invokes them. Provisioning includes an Android UI and copies the DPC into the new managed profile. Check managed users feature, actual profile owner, existing profile conflicts, OS patch and policy postconditions. A normal app can request provisioning. Profile-owner functions require the resulting role. [AOSP ManagedProvisioning caller check](https://android.googlesource.com/platform/packages/apps/ManagedProvisioning/+/refs/tags/aml_net_341610030/src/com/android/managedprovisioning/preprovisioning/PreProvisioningActivityController.java) · [DPM API](https://developer.android.com/reference/android/app/admin/DevicePolicyManager) · [Work profile behavior](https://developer.android.com/work/managed-profiles) |
| App sandbox and cross-profile bridges | Per-app UID and per-user storage protect private app data under platform policy. Work profiles share kernel, hardware, display and certain OS surfaces. Default and enterprise-approved intent links, contacts, input methods, notifications and document pickers need specific tests. Keep AGUS cross-profile allowlists and filters empty. Test default handlers and both directions. `DISALLOW_CROSS_PROFILE_COPY_PASTE` is direction-specific and does not alone secure personal clipboard input into work. `DISALLOW_SHARE_INTO_MANAGED_PROFILE` is a separate policy with its own scope. [AOSP app sandbox](https://source.android.com/docs/security/app-sandbox) · [UserManager restrictions](https://developer.android.com/reference/android/os/UserManager) · [DPC security](https://developer.android.com/work/dpc/security) |
| Install and lifecycle | `PackageInstaller.Session` supports staged writes, commit callbacks and possible Android confirmation. Documented silent paths depend on role, affiliation or specific installer/update conditions. Check the actual result on each eligible build. AGUS must verify both artifact bytes and certificate lineage, and account for device-wide package/version records shared by users. Profile policy can suspend packages (API 24+) and clear application user data (API 28+) subject to platform conditions. Check asynchronous results and per-profile uninstall independently. Profile deletion erases that profile and is a separate owner action. [Install session API](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session) · [DPM API](https://developer.android.com/reference/android/app/admin/DevicePolicyManager) · [AOSP package sign/install](https://source.android.com/docs/security/features/apksigning) |
| Developer test interface | Use a compiled debug/test-only adapter within the target APK. An authenticated explicit component or bound service can drive app-owned views and app-owned domain functions. Cross-publisher builds need signer checks on both sides with OS-derived caller identity, rules for rotation and a signed, expiring manifest. A same-signer signature permission is suitable for the lab. Android 15 AOSP enforces an instrumentation/target signature match and denies starting instrumentation on production builds to ordinary app callers without active instrumentation. The public Context method alone does not confer that privilege. UI Automator uses the instrumented `UiAutomation` connection, while Espresso and Orchestrator are interop targets for the dedicated lane. [AndroidX testing source](https://github.com/android/android-test) · [Android instrumentation](https://developer.android.com/training/testing/instrumented-tests) · [AOSP Android 15 enforcement](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-15.0.0_r1/services/core/java/com/android/server/am/ActivityManagerService.java#L16444) · [UI Automator](https://developer.android.com/training/testing/other-components/ui-automator) |
| Network | DPM always-on VPN with lockdown can be set by a profile owner for its user (API 24+, API 29+ for explicit lockdown allowlist). Test profile-wide VPN with an empty bypass list, fail-closed startup, user switches and DNS/IPv6/UDP/LAN semantics. Treat the VPN, proxy and approved upstream domains as independent controls. A VpnService on its own is packet routing. It does not supply a destination policy by default. Begin with an offline fixture that omits `INTERNET`. Profile policy and Android permission declarations need testing against platform handoff and apps with network permissions. [Android VPN](https://developer.android.com/develop/connectivity/vpn) · [DPM always-on VPN](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#setAlwaysOnVpnPackage(android.content.ComponentName,java.lang.String,boolean)) |
| Evidence and integrity | Android Keystore can protect a non-exportable signing key. Prefer a P-256 signing path with fresh server challenges and server-side verification, with optional hardware-backed claims verified using the full attestation chain, trusted root, revocation and application/boot claims. Verify StrongBox/TEE vs software and record absent signals. Play Integrity depends on ecosystem, project configuration and verified server-side nonce/request binding, with tiers and distribution limits. It does not establish AGUS user consent, profile cleanliness or truth of a submitted result. [Keystore](https://developer.android.com/privacy-and-security/keystore) · [Key attestation](https://developer.android.com/privacy-and-security/security-key-attestation) · [Play Integrity](https://developer.android.com/google/play/integrity/overview) |
| Foreground, stop and capture | A visible activity can keep its own screen awake. Background activity/foreground service starts, type restrictions and user-stop semantics constrain unattended execution. Avoid kiosk/lock task on contributor phones and preserve user navigation. A consenting MediaProjection session uses system UI and Android 14+ single-session tokens with app-window sharing support on eligible builds. MediaProjection can stop via system control or locking and secure surfaces remain protected. Start with structured evidence and app-owned render output with field redaction. Opaque protected steps are explicit evidence gaps. [Activity launch restrictions](https://developer.android.com/guide/components/activities/secure-bal) · [Awake screen flags](https://developer.android.com/develop/background-work/background-tasks/awake/screen-on) · [MediaProjection](https://developer.android.com/media/grow/media-projection) · [Lock task mode](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode) |

## Existing controllers and OS alternatives

| Technology | Upstream implementation and reuse decision |
| --- | --- |
| Test DPC | Apache-2.0 Google sample. Review its setup and provisioning activities for public extra/role behavior and profile UI. Its broad policy menu is a diagnostic reference. An AGUS DPC should ship only its narrow policy surface. [Pinned Test DPC source](https://github.com/googlesamples/android-testdpc/tree/e027da9bd9d88e9de77b4180b9457e72747bc374) |
| Shelter | GPL-3.0. Shows standard provisioning UI and a managed-profile copy of a controller, profile app management and freezing. File shuttle and cross-profile contacts behavior illustrate additional bridges and policies to omit and test. Use as a reference implementation. Redistribution of derived code would require license review and compliance. [Pinned Shelter mirror](https://github.com/PeterCxy/Shelter/tree/0afac87b2dc34e58652d6bb3cebb61b1baaf1b98) |
| Island and Insular | Island source reports Apache-2.0. Its work-profile setup and per-user app controls are relevant. Advanced modes include device-policy/ADB-dependent options outside the contributor tier. Insular documents itself as an Apache-2.0 Island fork with different dependencies and explicitly notes ROM failures and setup caveats. Review per-file notices and dependencies before any reuse. Validate on supported OEMs and avoid their broader policy/bridging surface. [Pinned Island](https://github.com/oasisfeng/island/tree/d63538212a9f417c180bdb9258c0f5461de53c27) · [Insular upstream and FAQ](https://secure-system.gitlab.io/Insular/faq.html) |
| Secondary user, private space and OEM clone features | Secondary users have a distinct Android user boundary, but available user counts, settings UX, switching, background behavior and management vary by OEM. DPM create/manage user generally needs device-owner authority. Private space is owner-controlled, can stop when locked, and is unsuitable as the centrally verifiable AGUS management substrate. OEM clone features provide no portable enrollment or policy API. Owner-switched secondary users are optional for annotated manual lab comparisons. [AOSP multi-user types](https://source.android.com/docs/devices/admin/multi-user) · [Android 15 private space](https://developer.android.com/about/versions/15/behavior-changes-all#private-space) |
| Accessibility | Technically can retrieve allowed UI trees and dispatch gestures with user enablement. Scope still creates unacceptable capture/control exposure for a default consumer tier. Google Play requires declarations, disclosure and consent where applicable, and identifies restrictions on autonomous initiation/planning/execution, with narrow exceptions including deterministic scripts and verified accessibility tools under their terms. No reliance on installing outside Play to avoid privacy or distribution controls. [Play Accessibility policy](https://support.google.com/googleplay/android-developer/answer/10964491) · [AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService) |
| Shizuku and LADB | Shizuku app Apache-2.0 and API MIT are separate projects. Server starts with ADB-shell or root privileges and brokers calls with that authority. LADB pairs a local ADB server using wireless debugging and has project-specific redistribution terms with a Play limitation. USB-free does not change either tool’s broad debugger trust boundary. Existing dedicated desktop runner is already the supported privileged path. [Pinned Shizuku and startup design](https://github.com/RikkaApps/Shizuku/tree/b844bc491f1790c72328e1a8e5b2349f8978f0ea) · [Shizuku API](https://github.com/RikkaApps/Shizuku-API) · [Pinned LADB](https://github.com/tytydraco/LADB/tree/60f48029cf9d8e0bc848ca41a7bd76694d4ab796) |
| Android Virtualization Framework | AVF uses pKVM and crosvm on eligible devices with protected-VM support and controlled privileges. Microdroid supplies a minimal execution environment without a full target Android app stack, Play wallet UI or access to OEM secure-wallet hardware through the same interfaces as the host. Later possibility for headless reviewed compute. No requirement for a custom Android guest in Phase 2. [AVF architecture](https://source.android.com/docs/core/virtualization/architecture) · [Microdroid](https://source.android.com/docs/core/virtualization/microdroid) |
| Host virtualization and containers | Phone Harness (MIT) demonstrates configurable, host-operated virtual device sessions. ReDroid uses Apache-2.0 project code, mixed upstream components, and Android-in-container with privileged Linux binder/kernel setup. Waydroid (GPL-3.0) uses Linux namespaces/container plumbing. Anbox is archived (GPL-3.0 umbrella, review component exceptions). Limbo (GPL-2.0 project) is QEMU-based general guest emulation on Android, with performance, guest OS image/GMS rights, protected wallet and thermal concerns. VirtualApp’s published implementation brokers Android app/framework behavior inside a host and has branch/version/commercial license caveats. It has no independently enforced per-customer Android user boundary. Suitable patterns are fixture reset and host orchestration on owned infrastructure. These engines provide no qualifying consumer-phone path for this pilot. [Phone Harness source](https://github.com/phone-harness/phone-harness/tree/f5096606b10eb757d03467944bccd82f8aba385f) · [ReDroid source](https://github.com/remote-android/redroid-doc/tree/eba9a489990f3f558b7115f25fdc782d610ee8ad) · [Waydroid](https://github.com/waydroid/waydroid) · [Anbox archive](https://github.com/anbox/anbox) · [Limbo](https://github.com/limboemu/limbo) · [VirtualApp source](https://github.com/asLody/VirtualApp/tree/7dc5a8c206c723af452bc340f1c4a8d57bb550c0) |
| Device farms, Appium and Maestro | Firebase Test Lab supports uploaded instrumented/real or virtual device tests. AWS Device Farm supports automated Appium and remote access to dedicated lab device sessions. Appium UiAutomator2 and Maestro are useful patterns for selectors, evidence and reproducibility. Their host-side tooling and installed test agents are a lab tier. Retain AGUS scenario differences for external device/OS coverage, and bucket it by farm/owned/emulator provenance. [Firebase Test Lab](https://firebase.google.com/docs/test-lab) · [AWS Device Farm Android testing](https://docs.aws.amazon.com/devicefarm/latest/developerguide/test-types-android-tests.html) · [Appium driver source](https://github.com/appium/appium-uiautomator2-driver/tree/95107daf8692cdcea2d2c989ef273e4fda9e6b88) · [Maestro source](https://github.com/mobile-dev-inc/maestro) |

## Distribution and Solana Mobile

Profile provisioning authority, partner APK distribution and AGUS app-store permission approval are separate. Confirm permitted DPC/managed private distribution, requested permissions, recurring provisioning UI and APK update policies before onboarding owners. Play's `REQUEST_INSTALL_PACKAGES` rules require eligible core functionality, declaration and user-initiated installs. Validate a managed private distribution path or an approved user-visible delivery path. Keep unattended install, dynamic code payloads and purchases disabled in the consumer offering until explicitly qualified. [Managed Google Play private apps](https://support.google.com/googleplay/work/answer/9495634) · [Play install-package policy](https://support.google.com/googleplay/android-developer/answer/12085295)

For MWA, use test wallet accounts and test endpoints. App authorization or a signature callback does not establish broadcast or finalized effects. Same-profile intent resolution, wallet store/update compatibility, OS prompts and Seed Vault availability require explicit acceptance per supported wallet and OS image. No AGUS path should ask for personal funds, seed, credentials, Secure Element access or autofill. Third-party wallet screens and biometrics remain attended and opaque. Keep transcript, participant judgment, canonical genesis and transaction verification outcomes separate. Hardware-backed Seeker features require attended genuine hardware, even when a simulator supports SDK development. [Official MWA Android guide](https://docs.solanamobile.com/android-native/using_mobile_wallet_adapter) · [Seed Vault SDK](https://github.com/solana-mobile/seed-vault-sdk) · [Existing AGUS wallet checks](../mobile-test/ARCHITECTURE.md)
