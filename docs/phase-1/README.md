# Phase 1 engineering decision

**Baseline** [`7a2ece4`](https://github.com/omnmlr/agus-ai/commit/7a2ece43d60732c4d2b2a054d0997515f90e302d) was `main` when the investigation began. The work is scoped to architecture, sources, and a disposable experiment. The passing Android 15 lab supports a bounded development architecture. The personal-device pilot requires separate hardware, policy and security acceptance. [Passing emulator workflow](https://github.com/omnmlr/agus-ai/actions/runs/45981236275)

## ADR 1 — Use a foreground managed profile and cooperating test builds

**Decision.** Use the Android system-managed work profile as the qualification and isolation candidate for ordinary contributor phones. The owner provisions it through Android’s consent UI. AGUS becomes **profile owner inside that profile**. A reviewed, uniquely named developer test build runs in the profile and exposes a short, compiled, authenticated test interface. The owner starts a foreground participation window. The runtime performs one approved workload at a time and offers owner-controlled stop and reclaim. Continue to support the existing dedicated device runner for broader test coverage.

**Rationale.** A work profile supplies a real Android user boundary and public management APIs. In-app hooks supply bounded execution inside the target’s real app process. The two address different requirements. Profile ownership conveys policy and package management authority within its scope. OS privilege, arbitrary input injection, wallet approval, and broad capture remain outside the phone offering. Tests through an SDK exercise instrumented builds, which may behave differently from production binaries. Report the exact variant. Existing hardware automation covers release-equivalent binaries and multi-app actions on dedicated devices. [Technical sources](android-research.md) · [Experimental evidence](experiments.md)

| Execution class | What can be commissioned | Boundary and rollout |
| --- | --- | --- |
| `phone_human` | Bug reproduction, onboarding and usability, attended disposable-wallet journeys, demonstrations, rubric evaluations, and agent corrections | First pilot candidate. Work-profile setup and artifact checks precede assignment. Contributors interact directly. Start with structured, user-reviewed observations. A separate opt-in governs any capture and any reuse for training. |
| `phone_cooperative` | Repeatable foreground app flows, app-owned assertions, bounded agent-selected semantic actions, and safe handoff to human interaction | Reviewed test build and reviewed action contract in the same work profile. Start with a first-party fixture. Every action is limited to a package, task, verb, budget and current lease. |
| `dedicated_runner` | Existing scripted and agent workloads, approved APKs, cross-app and release-build testing, and controlled MWA scenarios | Existing operator-reviewed catalog, outbound scoped credentials, local ADB, disposable data and verified cleanup. Device farms and AVDs are compatible extensions of this execution class with explicit provenance. |
| Owner-supported overnight window | Cooperative, reversible, pre-approved in-app flows on a charging and suitable device | Defer until physically validated. Start only from an unlocked foreground owner action. Waiting while the screen goes away, locked unattended launches, accidental approvals and silent capture are outside the pilot. |

A contributor with an existing employer profile, missing managed-user support, conflicting policies, degraded integrity, or unreliable cleanup is ineligible for the corresponding native lane. Do not replace an employer profile. An unsupported device may still qualify for a separate AGUS-owned sandbox evaluation that needs no external target, or the contributor can work on a qualified dedicated device. General APK testing stays in the dedicated tier. A device with no approved installation route can still use a first-party fixture bundled with the AGUS profile runtime for qualification and moderated evaluations.

### Runtime boundary

1. Owner authenticates, provisions, sees the exact profile admin capabilities, and completes technical and human qualification as appropriate. Separate personal UI from the profile-scoped executor. Prefer each copy talking to the backend independently. Default to zero AGUS cross-profile bridges.
2. Owner commits a foreground window with duration, charging and network constraints, evidence defaults, and an immediate Stop affordance. A schedule expresses eligibility. The scheduler can only allocate after local authorization and a fresh readiness proof.
3. Runtime obtains a fenced, short-lived lease. Verify manifest signature, APK bytes, package, signing lineage, version, exact activity, allowed SDK contract, partner endpoints, wallet mode, and installed state through supported APIs. Treat package code/version as shared across Android users for package collision/upgrade risk. Use dedicated test application IDs and reject updates to personal package IDs. Missing evidence fails closed.
4. Launch only the reviewed component. Bind caller and target identity with platform identity and package signer checks. A reviewed action takes typed, size-limited fixture inputs. The device verifies grant, current task and local budget for every action. The cooperating build must independently stop or reject stale commands. Agent models receive only the approved observation projection and submit proposed actions through the same executor.
5. Owner Back/Home/lock, explicit Stop, expiry, lost authority, scope violation, unhealthy power or temperature stop the session. Stop issuing actions even offline and quarantine until profile-scoped cleanup is acknowledged. A synthetic lab stop that depends on cooperation is insufficient for a general guarantee. Verify Android profile pause/removal as an independently user-controlled reclamation path.
6. Submit scoped evidence and clean up. Use an on-device key for claim signing and independently inspect action, rubric and chain evidence. Suspend/remove the package or clear pinned data with verified postconditions, revoke temporary credentials, and discard temporary evidence. Failed or ambiguous cleanup prevents new assignment.

## ADR 2 — Campaigns orchestrate existing runs

**Decision.** An immutable campaign revision contains task specs, coverage cells, rubric, evidence policy and compensation terms. One logical assignment fills one planned coverage slot. Each execution attempt has a single run and capability-bound lease where appropriate. Reuse the existing control plane, evidence and runner plumbing. The campaign coordinates outcomes, coverage and review. [Domain and API handoff](campaigns.md)

## ADR 3 — Gate product exposure independently of development

The medium-reasoning implementation session can begin with private, first-party fixtures and the explicit Phase 2 acceptance gates. Physical qualification, app-distribution review and a production threat-gate signoff determine personal-device pilot eligibility. General remote screen automation, arbitrary APKs, personal wallets, broad Accessibility, developer debugging privileges and device-owner provisioning are outside that pilot. No cloud activation, new vendor accounts, or physical purchases are dependencies of this research.
