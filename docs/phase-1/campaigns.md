# Campaigns, qualifications and API handoff

## Domain model

Keep existing identities, projects, artifact IDs, runs, and tenant authorization. Store all specs in immutable revisions. For a small pilot, model the records below through the existing control-plane transaction interface and bound metadata growth. Externally store evidence through the existing artifact abstraction. Move high-volume records to indexed tables before expanding concurrency if the existing single locked Postgres state row exceeds measured targets.

| Record | Required fields and constraints |
| --- | --- |
| `Campaign`, `CampaignRevision` | Owner/project, title, objective, revision and checksum, budget ceiling and asset, coverage matrix, due date, lifecycle, evidence and retention policy, requested export purpose. One launched revision per immutable execution scope. A changed scope creates a new revision and assignments. |
| `TaskSpec` | Revision ID, kind, eligible runtime classes, workload profile and authorized app/wallet recipe, optional build ID and authorization, versioned instructions and rubric, expected schema, time/action limits, permitted evidence, stop conditions and capability predicate. Separate attended and unattended steps. |
| `CoverageSlot`, `Assignment`, `Attempt` | Slot cohort and required count/group, logical assignment ID and immutable acceptable terms digest. Attempt number, server operation key, assigned contributor and device as appropriate, availability deadline, current run and lease generation, proof and acceptance refs. Unique current attempt per slot, one active lease per device, one active human assignment per contributor, and one accepted fulfillment per slot. Retries retain prior attempts and their evidence. |
| `RuntimeInstallation`, `DeviceQualification` | Pseudonymous device ID, owner, runtime class, app/profile enrollment key and public key history, attestation verdict with freshness, coarse observations, policy recipe and build fingerprint class, cleanup proof, qualification version and validity. No IMEI, account list, personal wallet, installed-app inventory, location history or USB serial. |
| `ContributorQualification`, `ReliabilitySnapshot` | Contributor ID, specialization tags, rubric version, calibrated pass or remediation decision, expiration and appeal. Evidence quality, completion, stop, connectivity and cleanup statistics with sample count, time window and provenance, split by cause and runtime. Employer or platform interruptions and valid owner stops should be represented without being treated as fraud. |
| `ConsentGrant` | Subject, role, purpose, immutable terms digest, scope (assignment and artifact types or export dataset), timestamp, expiry/revocation, retention and provenance. Store run permission and training reuse consent separately. |
| `Submission`, `EvidenceReview` | Immutable versions, run and task bindings, approved artifact digests and receipt, schema/rubric versions, rejection taxonomy and rationale, redaction status, review state, reviewer actor and audit trail. Corrections reference a specific action and before/after state. |
| `CompensationObligation` | Assignment/attempt, contributor and immutable payout terms, asset/atomic amount and basis, accepted work or recorded partial entitlement, reserved funding, acceptance ID, and settlement reference. Unique obligation per entitlement. Store payout metadata and signatures separately from evidence. |
| `ExportPackage` | Allowed purpose, scope/consent versions, review clearance, field-level schemas, pack hash, expiry and delivery audit. Track consent and redaction dependency so a withdrawal invalidates pending packages and future deliveries. |

Task kind is one of `automated_test`, `human_test`, `agent_evaluation`, `human_demonstration`, `agent_correction`. A training campaign sets a separate purpose on supported kinds and obeys training consent. Store human reproduction as ordered steps, expected/actual outcomes and app context. Demonstrations store typed, target-scoped actions, timestamps and optional motivation codes with explicit redaction. Corrections reference a particular version and step, issue category, corrected action, outcome and reviewer rationale. Agent comparisons pin environment, task/rubric version, action budget and model or external-client identifier. Keep calibration and holdout samples separate from authorized training sets.

### Qualification and matching

- **Device gate.** Compatible OS, OEM and ABI, actual supported profile policies, fresh signed enrollment challenge, reviewers’ build and profile compatibility, reproducible local isolation and cleanup fixture, minimum storage/memory, power and thermal checks, and recent short AGUS endpoint quality probe. Match on scenario-specific latency budgets, wallet capabilities and connectivity. Record unsupported measurements as absent. Device integrity and attestation signals are policy inputs with provenance, not a test outcome.
- **Human gate.** Run a short known-bug exercise and a structured reproduction with a consent/redaction check. Use rubric anchors with calibration examples. Require relevant specialization checks for wallets, accessibility/UX evaluation, agent corrections or optional languages. Let a reviewer adjudicate borderline decisions. Avoid arbitrary hardware, social, earnings or personal-data requirements for unrelated tasks.
- **Reliability.** Measure evidence acceptance, completeness, reviewer agreement, confirmed cleanup and time-to-report over a disclosed sample. Track false acceptance, provider or device causes separately, and reserve some eligible assignments for new qualified contributors. A single poor outcome or owner stop should be reviewed in context. Time-bound skill/capability assertions expire and are checked on claim, especially after a management, app signer, OS or integrity change.
- **Scheduling.** Filter with hard qualification, signer/artifact review, no conflict, fresh availability, training/capture flags and disclosed funding. Then rank by coverage shortfall, suitability, independence and deadlines. Trials use fixed per-assignment terms. A randomized device identifier groups repeats inside authorized aggregation. Avoid disclosing identifying small cohorts or payout-wallet addresses.

### State and authorization

- Campaign `draft → ready → active → closing → completed`, with `paused` and `cancelled` exits. Ready requires reviewed artifacts, rubrics, policy, and if applicable reserved budget. Cancelling withdraws unclaimed work, fences active attempts, waits for cleanup/reconciliation, and honors earned obligations. Summary reports distinguish unscheduled, attempted, accepted, missing coverage, assertion failure, stop, invalid and unresolved states.
- Assignment `open → reserved → active → submitted → in_review → accepted` or `needs_revision/rejected`. Separate attempt terminal states include `declined`, `expired`, `cancelled`, `interrupted`, and `voided`. A lease `granted → active → stopping → cleanup_pending → released` or expires with explicit unconfirmed cleanup. A cleanup failure quarantines the device. Human revision work resubmits a version of the same assignment. A replacement after interruption uses a fresh attempt/fence and obeys irreversible-action reconciliation. Prevent late uploads and duplicate payouts from a superseded attempt. Allow authorized, scoped post-expiry cleanup acknowledgements that cannot restore an expired grant.
- Evaluation uses its own supported assertions and pass/fail/unverified state. Evidence QA and work acceptance are distinct. Reviewers cannot judge their own contribution. Report actual matching coverage with denominator and known selection limits. Do not infer device assurance from model or self-reported evidence.
- Compensation flows `unfunded → reserved → earned → payout_pending → confirmed` with `needs_review`, `failed` and explicit refund/release reconciliation. Use unique funding/payout intents, compare-and-set and a persisted signed payload/signature before broadcast. Retain the existing Devnet test scope. General compensation remains disabled until explicitly approved funding, payout semantics, adjudication, refund and reconciliation are in place. An accepted bug report may be earned work even when the app fails its test.

## Proposed additive API surface

All routes are relative to `/api/v1`. Stable route names below are Phase 2 candidates. Use scoped bearer credentials, explicit request versions, idempotency keys on create/transition routes and `expectedRevision` or equivalent preconditions on writes. Return existing stable error envelopes. Match response fields to each actor’s authority.

| Surface | Request, response and boundary |
| --- | --- |
| `POST /me/runtime-enrollments`, `POST /me/runtime-enrollments/:id/complete` | Person request `{runtimeClass,appVersion,policyVersion}` → nonce and expiry. Complete with public key, signed binding and bounded profile/evidence verdict inputs → private pending installation. Verify fresh server challenge, invariant role and proof before issuing an independently scoped runtime credential. Person token never substitutes for a lease. |
| `POST /runtime/heartbeat`, `POST /runtime/claim` | Runtime-only request with installation ID, policy/check versions, rounded readings, current local foreground window and offer. Response returns leased assignment/run, fence, manifest digest, expiry/TTL, scopes, consent identity and artifact link. Keep the existing `/provider/*` transport and dedicated enrollment unchanged. |
| `GET/POST /campaigns`, `GET/PATCH /campaigns/:id`, `POST /campaigns/:id/launch` or `/pause`, `/cancel` | Project owner edits an expected draft revision. Launch validates and atomically creates coverage slots under the admitted budget. `GET /campaigns/:id/report` returns coverage counts, reviewer dispositions, grouped results/evidence, payout summary and missing cells. Use existing run drill-down and monotonic events with pagination. |
| `GET /me/qualifications`, `POST /me/qualifications/:id/submissions`, `GET /me/assignments`, `POST /me/assignments/:id/accept` or `/decline`, `/stop` | Person sees their eligibility, reason/remedy and scope-specific offers. Accept supplies qualification version, `termsDigest`, optional device and explicit choices. Authorize person and runtime assignments against the same expected plan. Show exact evidence policy and compensation before acceptance. |
| `GET /runtime/leases/:id`, `POST /runtime/leases/:id/events` or `/cleanup`, `/report` | Lease credential only. App verifies local TTL, fence, package and action scope. Server verifies envelope and idempotent sequence. Keep evidence references content-addressed and grant-scoped. Stop acknowledgements distinguish request, execution cessation and confirmed cleanup. |
| `POST /assignments/:id/submissions`, `POST /assignments/:id/reviews` | Actor scope, attempt ID, expected version, schema-bound rubric scores, content hashes, review reason codes and accepted terms. Reviewer-only acceptance CAS generates the compensation obligation once. Existing runs keep their separate sealed report/verification behavior. |
| `PUT/DELETE /me/assignments/:id/consents/:purpose`, `POST /campaigns/:id/exports`, `GET /campaigns/:id/exports/:exportId` | Actor grants or withdraws own specific rights. Developer export is deny-by-default unless authorization, subject consent, review and retention hold at generation **and** delivery. Redact and remove identifiers from the pack, bind exact artifacts, audit delivered bytes. Previously downloaded copies require recipient deletion/retention processes. Preserve legacy trajectory export. |

Possible conflict codes include `qualification_required`, `profile_unavailable`, `scope_changed`, `grant_expired`, `cleanup_unconfirmed`, `review_conflict` and `consent_withdrawn`. Browser and phone views use server statuses directly. An assignment response never exposes runner or lease secrets to a person client. Keep action policy and report schema versioned and update the generated types, CLI and MCP along with contract tests.

### Manifest and receipt bindings

Sign a canonical workload manifest outside the device. Bind version, audience, assignment/attempt/run/lease IDs, increasing lease fence, scenario and rubric versions, build ID, package, signer and APK SHA-256, exact component, allowed verbs and observation schema, resource and action limits, authorized endpoints, test-wallet recipe, evidence terms digest, random challenge, issue time, expiry and local TTL. Validate the same schema at claim, launch, action and evidence intake. Accept lease renewals only for the current fence and never extend the owner-approved window. Use a fresh monotonic timer after each valid response and discard authority on process restart until revalidated.

A versioned receipt reuses the existing run and artifact binding and includes the manifest digest, lease challenge/fence, installation and key ID, action and rubric versions, terminal outcome, evidence hashes and cleanup reference. Use a tagged algorithm with one canonical encoding per version. Preserve existing Ed25519 v1 verification. For a native v2 draft use Android Keystore ECDSA P-256/SHA-256 with ASN.1 DER signatures encoded as standard padded Base64. Select the algorithm and encoding from the enrolled key and receipt version, and reject conflicting caller parameters. Publish separate provenance fields for emulator/physical, claim signer, hardware attestation, human review and independent chain verification.

## UX handoff to Chisom

Android retains Home, Activity and Earnings as the existing integration anchors. Enrollment offers “Use this phone” and the existing dedicated runner path, with system profile setup, conflicting-profile help, check status and skill calibration. Job details show exactly what may be installed, owner control, evidence and payout terms. The active native flow has a persistent stop affordance within cooperating screens, owner-controlled Android reclaim, and clear stopped/cleanup-pending states. Human work shows step instructions, expected/actual, save or submit, feedback evidence preview, redaction and separate training rights. Device readiness, assignment acceptance and earnings are independent. Label Devnet test units explicitly in copy and data.

The web portal adds a campaign builder (build, lanes, cohorts, rubric, terms and evidence), launch review, coverage/report view and evidence review queue. Reuse project/build/run detail. Show missing cells and provenance next to results, surface independent chain checks and separate reviewer acceptance, and explain why exports are locked or withdrawn. Keep current run links and reference implementation intact. Deliver wire states and fixtures for Chisom before introducing visual changes. [Current frontend contract](../../FRONTEND_CONTRACT.md)
