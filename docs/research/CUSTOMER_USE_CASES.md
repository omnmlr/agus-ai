# What customers commission

Proposed service catalogue; not a list of currently deployed features or actual customer orders.

## A. Solana release assurance

Buyer: dApp release owner. Input: authorized APK hash, package/version, wallet versions, intended Android/Seeker coverage, test identities, success assertions. Campaign: repeat onboarding, connect, authorize, reject, sign, broadcast, resume and reconcile across a small matrix. Deliverable: compatibility matrix, reproducible failures, independently checked chain effects and signed run reports. Repeat on each release. Do not claim all wallet/security properties were tested.

## B. Human usability and onboarding

Buyer: mobile product team. Input: 10–30 qualified participants (illustrative), target experience level, language and devices, test accounts and task instructions. Ask participants to complete onboarding without guidance, then answer neutral questions and report confusing states. Deliverable: denominator-based completion rates, time distribution, severity-ranked issues with redacted evidence, and actionable suggestions. Do not generalize a convenience sample to all customers.

## C. Bug reproduction

Buyer: wallet, SDK or dApp support team. Input: reported environment, authorized build, reproducible symptom and bounded scope. Match appropriate hardware, app/wallet versions and connectivity. Report reproduction/non-reproduction, exact steps, minimal evidence and relevant callback/chain result. Do not claim root cause without evidence.

## D. Human demonstration and agent correction

Buyer: authorized agent/data team. Input: versioned task, permitted app/test environment, objective outcome, annotation schema, retention and data rights. Contributor completes a demonstration or corrects a failed agent action. Deliverable: time-aligned, redacted action/outcome trajectory with provenance; human and model actions separated. Buyer approves quality via rubric. No capture of unrelated phone activity.

## E. Agent evaluation

Buyer: financial-agent developer. Input: agent endpoint or approved bounded action client, same task initial states and budgets, independent success assertion. Compare human baseline, scripted baseline and agent where appropriate. Deliverable: success/failure, false-success rate, steps/time, recovery, unauthorized-action attempts, actual cost and confidence intervals when justified.

## Campaign contract

A campaign binds exact build and allowed targets, requested device and contributor qualifications, task version, allocation count, instructions, objective and subjective rubrics, time/deadline, fixed compensation, authorized evidence, retention and review rules. Use explicit states: draft → published → assigned → active → submitted → reviewed → accepted/revision/rejected → settlement/reconciliation. Allow cancellation with transparent payment handling. Reuse existing execution records; do not conflate successful work with a passing app assertion.

Report each metric's denominator, missing data, test mode, device provenance and environment. For campaign aggregation, deduplicate by symptom and conditions, keep raw authorized evidence access-controlled, and show sample composition. Example: 8/10 wallet connects passed; 2 failed after resume on a pinned configuration. That is illustrative, not a real finding.

## Buyer value and success criteria

Return a report a release owner can act on without further manual investigation. Target faster reproduction, incremental defects, fewer repeat regressions and independent financial outcomes. For AI teams, prioritize reproducibility and label quality rather than maximum trajectory volume. Neither a beautiful dashboard nor a large pool of idle devices is the deliverable.
